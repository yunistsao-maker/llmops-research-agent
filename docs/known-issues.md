# 獨立檢查的結果，與仍然存在的限制

這份專案除了自己的測試之外，交付前另外請了彼此獨立的檢查者來攻擊它：每一輪由兩個（第一輪四個）沒有看過先前討論的檢查者，
分別針對 agent 的驗證規則、發布流程與操作工具，寫出可以重現的腳本。這份文件記錄每一輪找到什麼、怎麼處理，以及**修正之後仍然存在的限制**。

數字（測試數量、執行結果）在 [README](../README.md) 第 2 節。

## 先講結論：怎麼用這一版

1. **預設是 `PublishMode=review`**（template 的預設值）：每一份提案都由妳核准。建議先這樣跑幾週（[delivery plan](delivery-plan.md) Phase 2）。
2. **改成 `auto` 之後，不經過人就上線的只有兩類變更**：新增的內容（新紀錄、附加的備註、多引用一個來源、新的 digest），以及既有紀錄上
   日期、數字、版本的變更。其他對既有紀錄的修改都等妳核准。這個範圍是第三輪檢查之後刻意收窄的：程式能逐字對照引文的才交給程式。
3. **核准時以「實際差異」為準**：`portalctl show <id>` 最前面列的原值 → 新值是對**現在上線的資料**重算的，每個值完整列出；逐項對照它的引文與來源網址。
4. 下面「仍然存在的限制」是核准時值得多看一眼的地方，也是決定要不要用 `auto` 時該知道的事。

## 第三輪找到的問題怎麼處理

第三輪的結論不只是「補三十幾個洞」：其中一類問題沒有辦法靠多寫規則解決。狀態、分類、識別字串、一段文字——這些值**沒有任何程式能拿去和引文逐字比對**，
所以原本「通過驗證就自動發布」的設計，對這類變更其實是沒有人把關的。這一版因此改了政策，而不只是修規則：

| 類別 | 第三輪的問題 | 現在的做法 |
| --- | --- | --- |
| **政策** | 狀態、是／否、分類、識別字串、文字改寫、標籤、清單順序、清空文字：只要有一則提到模型名稱的引文就能自動上線 | `auto` 只自己發布新增的內容與日期／數字／版本的變更；上述每一種對既有紀錄的修改都等人核准。驗證器會先警告模型「這一項會等人」。template 的預設改成 `review` |
| 來源層級 | 網址字面就決定層級（`…/releases/../issues/123` 算官方）；PyPI、社群論壇、Marketplace 整個網域算官方；portal 引用過一頁，整站都算數 | 層級看實際抓到的網址；路徑不穩定的網址不抓；任何人都能發文的頁面一律是 community；portal 引用過的只算那一頁；公司認定的官方網域用 `EXTRA_OFFICIAL_DOMAINS` |
| 一項事實一則引文 | 層級取所有引文裡最高的、數值在全部引文裡找：一則官方引文加一則論壇貼文就能改官方的日期 | 每個日期、數字、版本要在**同一則**引文裡，而且那一則要講這個模型、層級也夠 |
| 對象 | 名稱片段比對（Sonnet 5 = Sonnet 5.5）、引文可以跨兩列、任何標題都算數、紀錄可以自己改名來配合引文 | 名稱整個比對；值屬於同一列裡它前面最近的名稱；只看包住引文的那幾層標題；沒有名稱的紀錄直接退回 |
| 日期與格式 | `"2026-10-02\n"` 通過 schema；全形數字的 `createdAt` 讓時間規則失效 | 日期與時間一律用嚴格的 ASCII 格式比對，兩端都擋；讀不懂的時間直接拒絕 |
| 版本與數字 | `v2`、`litellm_v1.40.0` 不算版本；任何數字乘以 1000 都算數；名稱與日期裡的數字也算 | 版本整個比對（含 `rc`／`stable` 等寫法）；千分換算只限價格欄位；名稱、id、日期裡的數字不算 |
| 標籤與引用 | 標籤可以沒有依據地調高；引用來源整批換成自稱官方的新來源；`conflicts`、`replacement` 不需要夠格的引文 | 調高標籤等於重新主張底下每個值；新來源的層級由它的網址決定；`conflicts` 與 `replacement` 要出自講這個模型的引文；任何標籤變更都等人 |
| 沒有標籤的位置 | catalog 模型層級與 deep dive 接受任何層級的來源 | 每個位置都有層級下限（[agent](agent.md) 第 2 節） |
| digest | 可以完全沒有引文；日期只要出現在 portal 任何地方 | 每一則都要引用來源；日期與金額要出自它引用且這次讀過的頁面，或它提到的模型的紀錄；沒有重新讀取的項目會讓提案等人 |
| 文字裡的日期、金額、連結 | 只認 `YYYY-MM-DD` 與 `$數字`；多種寫法的連結看不到 | 認得常見的日期與金額寫法（含中文）；連結的辨認先還原全形字、隱形字元與緊貼的符號 |
| 位置路徑 | `/events/2/date` 在清單變動後改到另一筆 | 路徑中途不能用位置，要用 id |
| 發布端的形狀檢查 | 不是字串的 rationale、引文紀錄的任何欄位、`portal.manifest`、`add` 的 `before` 沒有人看；沒有引文的 operation 也發布；超大的整數與檔案 | 全部在發布端拒絕 |
| 蓋章（`asOf`／`lastVerified`／`accessed`） | 採信紀錄自己寫的數字 | 從紀錄的頁面清單與引文自己算；`accessed` 只給真的被引用到的頁面 |
| 待核准紀錄 | 自動發布會刪掉同 id、不同內容的待核准提案；捨棄後重送的無法核准；已上線的還能被捨棄 | 待核准的提案只有內容相同時才會被清掉；捨棄的可以重送再核准；已上線的不能捨棄 |
| 重試與通知 | 重試到的核准回報失敗、重試到的自動發布只寄「no change」；通知寄不出去時 execution 成功；`mode` 寫錯要等研究跑完 | 同一個請求送兩次得到第一次的答案；通知失敗以 `PortalNotificationFailed` 結束；execution 的 `mode` 在啟動研究之前檢查（stack 的發布設定由 Publish 這一步讀，見第四輪）|
| 團隊的測試欄位 | `litellm.status` 的 `tested-*`、`measuredBy: internal`、帶內部實測的紀錄的識別欄位可以被 agent 改 | 全部列為保護欄位 |
| rollback、暫停原因 | 可以 rollback 到從未上線過的 release；暫停原因原樣印到終端機 | 目標必須在發布紀錄裡（`--unlisted` 例外）；原因寫入時就清乾淨 |
| `portalctl` | `PIPELINE_STATE_URI` 被用在指令列指定的資料位置上；`publish s3://別處/…` 發布的是另一份；`push` 把略過的檔案當成刪除、`pull` 把刻意刪掉的寫回來；`show` 截斷長的值 | 見 [runbook](runbook.md)：各自修正，並在輸出裡說明用的是哪一份清單、略過了什麼 |
| 檢視器、`ui_smoke`、`configure_agent` | 檢視器顯示的和發布的不是同一份提案；UI 顯示舊資料時 `ui_smoke` 仍然通過；`--check` 對不成對的位置回報正確 | 檢視器和發布端用同一條規則挑提案；`ui_smoke` 改成看「先前讀過的檔案有沒有從新版重讀」與「畫面上的文字有沒有跟著變」；`--check` 會指出不成對的位置 |
| 效能與穩定性 | 特製的頁面讓掃描花數分鐘；半個 emoji 讓結果存不了檔；網址裡不成對的 `[` 讓工具失敗 | 同樣的特製輸入現在都在一秒內處理完（有測試），頁面與提案另有大小上限；存檔前清理不成對的字元；工具把這類網址當成一般的錯誤回報 |
| 誤擋 | 名稱很短的模型（`o3`）、自訂 id 的公告、digest 裡的舊值與期限被退回；一般 API 文件的句子被當成指令 | 各自放寬；掃描改成以精確為先 |

## 第四輪

第四輪的對象是第三輪修正之後的版本。兩位檢查者一共提出 **44 項**可以重現的問題：agent 的驗證器 24 項（16 項高、7 項中、1 項低），
發布流程與工具 20 項（6 項高、9 項中、5 項低）；另外請第三位檢查者對測試做 mutation 檢查——故意改壞 259 處程式，看測試發不發現——有 32 處沒有被發現。
這一版對每一項都做了處理（修正並補測試，少數幾項改的是文件），每一支重現腳本都重新執行過。

這一輪同樣有「不能靠多寫幾條規則解決」的部分，所以改了三個做法：

1. **引文是頁面上完整的單位。** 以前模型可以只引一列的後半段（少了名稱那一格），程式就把它當成另一個模型的值。現在 `record_evidence` 會把片段擴成它碰到的
   整列、整句或整個標題，存下來的是擴充後的文字，連同它所在的標題與表頭。核准的人看到的也是完整的一列。
2. **程式拿不準就說拿不準。** 「這則引文講的是不是這個模型」以前只有是與否；頁面的寫法千變萬化，硬要二選一就會把錯的放行、把對的退回（兩種這一輪都找到了）。
   現在有第三種答案「不確定」：提案照樣成立，但帶上旗標，發布端看到旗標一律等人。所以 `auto` 模式下自己上線的，是程式**確定**的那些。
3. **「可以逐字對照」看的是變更，不是新值的長相。** 以前只要新值長得像日期，就當成「日期的變更」放行——一段備註、一個模型名稱因此可以被一個日期蓋掉。
   現在要同類換同類（日期→日期、數字→數字、版本→版本）才算。

| 類別 | 第四輪的問題 | 現在的做法 |
| --- | --- | --- |
| 引文是片段 | 引一列的後半段、上一列的尾巴接下一列的開頭、沒有名稱格的價格列：值被算到別的模型頭上（測試資料裡 Sonnet 4.5 的退役日可以發布成 Sonnet 5.5 的） | 引文擴成完整的列／句／標題再判斷；長度有上限；同一段文字出現多次時用行號指定 |
| 值是誰的 | 「migrate from X to Y before D」把 D 算給替代品 Y、誠實的 X 反而被退回；程式不認得的名稱被當成「沒有名稱」，它的值掉到前一個模型頭上；`GPT-4o Audio Preview` 被讀成 gpt-4o；新紀錄可以同時帶兩個模型的名稱；Bedrock 的一列可以支持 Foundry 紀錄的日期 | 三種答案（是／不是／不確定），規則在 [agent](agent.md) 第 2 節「對象」；不認得的名稱、兩個名稱分不出誰是誰、沒提到紀錄所屬的平台、另一種計價，都是「不確定」→ 等人；新紀錄的名稱欄位要一致 |
| 頁面怎麼讀 | 註腳記號黏在值上（`$3¹` 讀成 31、`2026-11-30¹` 讀不到日期）；刪除線裡的舊值照樣算數；JSON／純文字頁面拿網址當標題，網址裡寫了模型名稱就算「在講它」；分頁、手風琴、更新紀錄（日期寫在標題）、跨列儲存格的版面讀不對 | 註腳記號與刪除線的內容不讀；網址的 query／fragment 與「標題就是網址」不當依據；分頁的標籤跟著它的內容、標題裡的按鈕文字留著、Markdown 標題、跨列儲存格、寫在標題上的日期與版本都讀得到 |
| 來源層級 | 子網域繼承上層的規則（`test.pypi.org` 算官方、`community.` 開頭的論壇算公告來源）；路徑規則可以用 `//`、`%6d`、大小寫、`;x` 繞過 | 規則以主機為準，子網域要明講；像公開發文區的子網域不算；路徑規則不分大小寫，寫法古怪的路徑一律 community。`EXTRA_OFFICIAL_DOMAINS` 的語意跟著改了（見下面的限制） |
| LiteLLM 的欄位 | `data/litellm.json` 沒有「對象」：AWS 頁面上的「Boto3 version 1.40.0」可以變成 LiteLLM 的建議版本、「Requires Python 3.9.2」變成最低基準、別的套件的 CVE 變成 LiteLLM 的公告；版本只比第一個標記（`.patch.1` 的引文支持 `.patch.9`） | 對象是 LiteLLM 這個產品：引文、上下文或主機要點名它；別的軟體和它的版本號歸那個軟體；版本整串比對；沒有公開編號的公告、不是版本的版本欄位等人 |
| 數字與日期 | 句子裡任何地方出現「per 1,000」，每個數字都乘 1000（每百萬 $3 發布成 3000）；`11/10/2026` 兩種讀法都算數；「Claude Haiku 4.5 October 2026」讀成 10 月 5 日；時間、HTTP 狀態碼被當成數字；一長串數字讓驗證花半分鐘 | 只有和「每千 token」寫在一起的那個數字才換算；兩種讀法都成立的日期是「不確定」；名稱後面的數字是名稱的一部分；時間與狀態碼不算；那個輸入現在不到一秒（有測試）。另外認得更多寫法（`30.11.2026`、`30-Nov-2026`、德文、韓文、民國年、`100万`、`1 000 000`） |
| 什麼算日期／數字／版本的變更 | 看新值的形狀：備註、`modelName`、`providerModelId`、摘要被換成一個日期，或版本欄位被換成一段含版本號的文字，在 `auto` 模式直接上線 | 看變更：同類換同類才算，其餘是改寫，等人（agent 與發布端用同一條規則） |
| 清單 | 「新增」一筆和既有紀錄同 key 的紀錄（功能、服務、價格範圍、release 版本、別名）或把新紀錄插在最前面：頁面顯示的變成新的那一筆——包括團隊實測過的紀錄；引用來源被調換順序、備註被改寫或刪除 | 同 key 的新增一律拒絕；插在既有紀錄前面等人；引用來源只能從尾端增加 |
| `replacement` | 寫成「(gpt-6-luna)」、「@gpt-6-luna」、前後補空白、或只寫「GPT」，就不需要任何引文 | 讀不出一個可用的名稱就退回 |
| 新增文字裡的日期、金額、連結 | 只認幾種 ASCII 寫法：零寬字元、特殊連字號、全形 `$`、`31.03.2027`、民國年、沒有 `https://` 的網址、`//host`、`ftp://`、IP，都看不到 | 先還原再讀；更多日期與金額的寫法；沒有年份的日子也算（見 agent 第 2 節）；各種寫法的網址都當成連結 |
| digest | 沒有任何項目、沒有讀任何頁面、沒有任何引文的 digest（只有 headline 與 action items）可以上線；只要提到某個模型，它的日期就能拿來用在另一個模型上；`relatedModelIds` 可以填事件的 id | 至少一則項目；日期與金額要有引文而且是**句子說的那個模型**的，或 portal 上那個模型的紀錄；headline 與 action items 只能重複項目已經成立的；程式判斷不了的等人（旗標見 agent 第 2 節） |
| 注入掃描 | 16 句直白的「對 AI 喊話」沒有被標記、3 句普通的句子被誤標；沒被標記的一句寫進了備註，下一次研究又從 portal 讀回來 | 補上對 AI／語言模型／提案喊話的句型並收窄誤判的；portal 的資料回給模型時註明是資料，像指令的不給看並加旗標。仍然是啟發式的 |
| 誤擋 | 兩個模型共用一個日期的句子、「same as Claude Sonnet 5: $3」、「Claude Code」「Claude Pro and Max」被當成模型名稱；更新紀錄、重複的列、分頁等版面讓誠實的提案提不出來 | 各自修正（並列的名稱共用後面的值、產品名稱不是模型、用行號指定是哪一列…）。規則變嚴之後，預期會有更多更新走核准而不是被退回 |
| 發布端：印出來的內容 | `portalctl show` 把提案裡的文字印在行首，可以偽造成工具自己的指令；用看不見的填充字元（U+2800）把文字推到下一行行首 | 從提案來的文字一律標示並折行，接續的行以 `┆` 開頭；看起來是空白的字元先還原 |
| 發布端：Gateway 頁面 | 每一項檢查都通過的版本字串上線後，讓 Gateway 頁面的版本比較當掉 | 版本欄位照頁面實際解析的格式檢查，不去頭去尾 |
| 發布端：旗標 | 發布端讀不懂的旗標內容被當成「沒有旗標」 | 任何旗標、任何內容都算有 |
| 待核准與 `portalctl` | 核准→rollback→重新送出的提案永遠無法捨棄；`pull` 有衝突時只更新一半，下一次 `push` 把沒更新的檔案當成妳的修改重新發布；`pull --dry-run` 預覽到會停下來卻回報成功；`PIPELINE_RESEARCH_URI` 被套用在指令列指定的資料位置上；checkout 裡多了 `runs/perf (copy)/` 時，`runs/perf/` 的刪除不會被發布 | 內容已經不在線上的提案可以捨棄；`pull` 有衝突時什麼都不寫，`--dry-run` 回報 exit 4；研究結果的位置和待核准清單用同一條規則（另有 `--research`）；略過的路徑照原樣記錄 |
| 檢視器與檢查工具 | 檢視器沒有畫出 digest 的三種文字（發布端卻會發布）；`ui_smoke.py` 對四種壞掉的 UI 回報全部通過；`patch_ui.py --check` 對仍然自己讀資料的頁面回報「全部已套用」（`window.fetch`、`XMLHttpRequest`、把資料檔 import 進程式…） | 檢視器畫出 digest 的每一段文字（有測試逐字比對）；`ui_smoke.py` 多檢查：每個資料檔在發布與 rollback 之後畫面上的文字、有沒有資料是從網站本身讀的、含標記的錯誤訊息、token 有沒有出現在標題／屬性／console；`patch_ui.py` 認得更多寫法（它仍然是文字比對，見限制） |
| UI：讀到別的 release | 連結裡的 id 可以帶 `../`（`#/digest/..%2F..%2F..%2F<另一個 release>%2F…`），頁面就去讀另一個 release 的檔案——例如已經 rollback 的那一版——而頁尾寫的是上線中的版本 | 設定了資料位置時，UI kit 只接受單純的相對路徑（和儲存端同一條規則），不合的不發出 request；`ui_smoke.py` 會實際打開這種連結確認 |
| 穩定性 | 拒絕一份 1 MB 的畸形提案需要 1.3 GB 記憶體（Publish function 只有 1 GB）：execution 變紅，卻沒有拒絕的原因；execution 的 input 裡有半個 emoji 時，每一步都失敗、連失敗報告也失敗：紅色、沒有通知 | 提案有值的數量上限（30,000），schema 錯誤只逐條列前 200 個：範圍內最糟的情況約 115 MB（有測試）；半個 emoji 換成 `�`、巢狀過深的 input 是被拒絕的請求；失敗報告不管 state 裡有什麼都會產生；連它都失敗時，state machine 自己寄一則固定內容的通知 |
| 文件與實際不符 | 文件說「設定在啟動研究之前檢查」，但發布的設定是 Publish function 的環境變數，啟動研究的那一步看不到 | 改文件：啟動前檢查的是 execution 的 input；發布設定由 CloudFormation 參數限制合法值，手動改壞時由 Publish 停下來，研究結果仍在、可以直接重新發布 |
| 測試沒發現的 32 處 | 例如：`remove` 沒有原值也接受、`runKey` 只檢查開頭、沒有設 `PUBLISH_MODE` 時變成自動發布、template 的預設改成 `auto`、`before` 用 `==` 比較（`True` 等於 `1`）… | 26 處補了會失敗的測試（其中幾處是真的缺口，一併修正）；2 處其實是同一個改法，改了也沒有任何行為差異；4 處所在的程式在這一輪重寫過，重寫後對應的規則有測試守著。修正之後整套 mutation 檢查重新跑過，又找到 11 處測試沒守住的規則（程式本身沒有錯），都補上了——數字與細節在 README 第 2 節 |

**這一輪的修正本身，還沒有再經過一輪獨立檢查。** 它們通過了檢查者原本的重現腳本與新增的測試，但改動的範圍很大（對象判斷整個重寫），
依照前四輪的經驗，新的規則裡很可能還有檢查者找得到的缺口。這是建議先用 `review` 模式運轉的另一個理由。

## 仍然存在的限制

這些不是「還沒修的 bug」，而是這個設計做不到、或選擇不做的事。

**信任邊界**

- **發布流程不防偽造的研究紀錄。** 它不信任提案的內容（一切從重新套用的結果判斷），但引文是不是真的出自那個頁面，發布端不會重新去抓來比對。
  能寫入 `research/` 的身分等於「可以提案」：內容仍然要通過 schema、保護欄位與每一道關卡，但在 `auto` 模式下，一份偽造得夠像的紀錄可以讓新增的內容與
  日期／數字／版本上線。`research/` 的寫入權限平常只有 runtime 的 role；需要更高的保證時用 `review`。
- **來源層級是一份寫死的規則表。** 沒列在表裡的網域是 community（不會被當成官方）；列為官方的網域如果本身被入侵或內容有誤，agent 會照著引用。
- **`EXTRA_OFFICIAL_DOMAINS` 的語意在這一版改了。** 只寫主機（`notices.example.com`）時，它涵蓋那個主機與子網域，但**只對內建規則不認得的主機有效**：
  不能用它把內建規則判成 community 的主機（例如 `github.com`）整個升成官方。要認定那種主機上的某個位置，寫成主機加路徑（`github.com/acme/notices`）。
  上一版設定過這個變數的話，請照新的寫法檢查一次。

**驗證器確認的是「有出處」，不是「讀對了」**

- **新增的文字沒有辦法查證。** 新的備註、新紀錄的說明、digest 的內文會在 `auto` 模式下直接發布；程式檢查的是裡面的日期、金額與連結，
  不是那句話說得對不對。（改寫**既有**的文字則一律等人。）文字裡出現**當天的日期**不需要出處。
- **「不確定」是設計出來的出口，會讓比較多的更新等人。** 一列裡有兩個模型名稱、名稱後面接著程式不認得的字、頁面沒有提到紀錄所屬的平台、日期有兩種讀法——
  這些情況程式不猜，提案帶著旗標等妳看。真實的頁面有多常落在這裡，只能在平行運轉時觀察；常見的版面如果老是「不確定」，那是值得回報的問題。
- **digest 多半會等人。** digest 的句子用同一套規則檢查：日期與金額要有引文而且是句子說的那個模型的。妳現有的 digest 習慣把日期寫成 `10-20` 這種短寫——
  這種寫法沒有年份、也可能是範圍，程式不對照，只讓提案等人（`uncheckedValue`）。prompt 已經要求 agent 寫完整的 `YYYY-MM-DD`；
  在它穩定做到之前，含 digest 的每週提案在 `auto` 模式下大多會走核准。digest 內文裡日期與金額以外的敘述，程式不檢查。
- **不是「每千 token」的價格單位不換算。** 頁面用「每十萬 token」這類單位標價時，換算成 portal 的每百萬價格會被退回（引文裡沒有那個數字）；這種來源要人工處理。
- **值在同一列的哪一欄，程式不知道。** 引文是「Claude X | $3 | $15」時，3 與 15 都算「講 Claude X 的數字」：把輸出價格寫成 3 不會被擋。
  日期也一樣（同一列有 deprecation 與 retirement 兩個日期）。核准時請對照引文確認欄位。
- **新紀錄裡的狀態與分類不和引文比對。** 一筆新的 lifecycle 事件，日期與模型名稱有引文把關，`event` 寫的是 `retirement` 還是 `deprecation` 沒有。
- **對象的判斷是啟發式的。** 模型名稱寫在表頭、值在下面各列的「轉置表格」，或同一格裡寫了好幾個模型的頁面，可能被誤擋，也可能被歸到錯的模型。
  官方頁面常見的版面都有測試，但版面千變萬化。
- **注入掃描是啟發式的**：會漏，也偶爾誤判；它只決定「要不要請人看一眼」。第四輪補上的句型只是檢查者實際寫出來的那些。

**還沒有在真實環境驗證的事**

- 兩個 stack 的實際部署、IAM 的實際行為、CloudFront 的實際回應、arm64 的 Lambda bundle：見 README 第 2 節的「尚未驗證」。
- **真實模型的研究品質**：測試用的是腳本化的模型。真實模型被這些規則退回時改不改得過來、會不會因為規則嚴格而常常交不出提案，要在平行運轉時觀察。
  規則收窄之後，`auto` 模式下會有比較多的更新走核准，這是預期的。第四輪之後 prompt 整個重寫過（整列引文、行號、哪些情況會等人），同樣只用腳本化模型測過。
- **state machine 新增的 `NotifyUnreported`**（失敗報告產生不出來時，由 state machine 自己寄通知）用了 `States.Format`：它在兩個本機的 ASL 引擎上執行過，
  沒有在 AWS 上執行過。template 通過 cfn-lint；如果 CloudFormation 部署時對這個狀態的定義有意見，錯誤會出現在更新 pipeline stack 的那一步，不會影響已經在跑的版本。

**工具**

- `ui_smoke.py` 靠「資料檔裡的一段文字完整顯示在某一頁」來確認內容有更新；UI 如果把所有文字都截短或轉換過再顯示，這項檢查會回報找不到可比對的文字（算失敗）。
  它現在也要求「沒有任何資料是從網站本身讀的」：UI 如果真的有自己的 JSON（例如翻譯檔），用 `--allow-site-file <樣式>` 指明。
- **`patch_ui.py --check` 是對原始碼做文字比對**：它認得的是列出來的那些寫法（各種 `fetch`、`XMLHttpRequest`、把資料檔 import 進程式、把資料路徑交給 loaders 以外的函式）。
  用別的 HTTP 函式庫、或把路徑拆開來組的程式它看不到。**證明「頁面沒有繞過資料位置」的是 `ui_smoke.py`**：它看的是瀏覽器實際發出的 request 與畫面上的文字。
- **提案有大小上限**：2 MB、500 個 operation、30,000 個值（agent 自己的上限更低）。超過的直接拒絕，不逐項處理。agent 不會寫出這種提案；手動編輯的大量修改請用 `pull`／`push`。
- execution 的 input、或 `portalctl` 的參數裡只有半個的 emoji（被截斷的文字）：input 裡的會被換成 `�` 再處理，指令列上的會被拒絕並請妳修正。
- `portalctl show` 重算差異需要讀資料位置的權限；沒有的時候它會改列提案暫存時記下的差異（超過 4,000 字元的值是截斷的），並說明原因。
